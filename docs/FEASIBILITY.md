# 《规则掠夺者 RULE THIEF》完整实现可行性分析

> 评估对象：[设计文档 V1](./RULE_THIEF_design_v1.html)  
> 评估日期：2026-10-25  
> 评估结论：**可以完整实现，技术上没有硬阻塞**。真正的成本在“调到好玩”和表现层，不在系统能不能写出来。

## 1. 结论速览

### 1.1 可行性判断

| 维度 | 判断 | 说明 |
|---|---|---|
| 功能范围 | 高可行性 | 单机、无后端、无联机、无程序化迷宫；所有系统都有明确上限 |
| 技术实现 | 高可行性 | 移动、自动瞄准、弹道、状态、波次、BOSS、触控均有成熟做法 |
| 内容量 | 中等 | 6 普通敌人、2 精英、1 三阶段 BOSS、9 组合、4 事件、13 房 |
| 规则组合风险 | 可控 | 用统一结算管线 + 触发预算，不做 9 套技能类 |
| 调优风险 | 中高 | 3 分钟是否好玩、15 分钟是否拖、BOSS 是否公平，只能靠试玩校准 |
| 移动端风险 | 中 | 竖屏/横屏、安全区、触控手感、性能需要真机验收 |
| 美术/音频风险 | 中 | 低美术成本可做，但达到设计稿的氛围需要额外投入 |
| 综合 | **可完整实现** | 无硬阻塞；建议先做 3 分钟切片再全量 |

### 1.2 时间判断

| 交付物 | 预计有效日 | 说明 |
|---|---:|---|
| 3 分钟切片（M0 + 弹射/爆裂） | 0.5–1 | 1 房间、1 玩家、2 敌人、基础魔弹、闪避、死亡重开 |
| 全功能可通关（M1–M3） | 7–11 | 规则、房间、6 敌人、精英、突变、事件、BOSS、结算 |
| 移动端/音频/UI/部署（M5） | 2–3 | 触控、响应式、音效、性能、静态构建 |
| 发布级调优（M4） | 3–5 | 数值、节奏、公平性、5–10 人试玩修正 |
| **合计** | **12–19 有效日** | 非连续投入约 3 周；AI 可压缩编码，但压缩不了调优和真机验收 |

> “有效日”按 6–8 小时聚焦开发估算。与设计文档的 13–23 天基本一致；本评估把编码阶段估得更紧，是因为有 AI 辅助，且首版明确不做 meta、联机、背包等系统。

### 1.3 重要前提

- 设计文档里的 M0–M5 “已完成”是 HTML 页面保存在浏览器 `localStorage` 的勾选状态，不是项目代码状态。
- 当前工作区 `Game` 目录未发现同名实现；本评估按**从零开始**计算。
- 设计文档中的“交互式规则组合实验室”“战斗可视化”是**设计稿演示**，不是游戏必需功能；首版可以不做，或用主菜单图鉴替代。
- 文档内两张 AI 插图可作为氛围/菜单参考；是否直接作为正式素材，需要确认来源与一致性。

## 2. 需求盘点

### 2.1 核心参数

| 项目 | 文档定义 |
|---|---|
| 视角/类型 | 俯视角动作肉鸽，自动攻击 + 手动闪避 |
| 平台 | PC / 手机网页，单人 |
| 单局目标 | 15 分钟（10–20 分钟区间） |
| 初始 HP | 100 |
| 自动攻击间隔 | 0.65s |
| 魔弹基础伤害 | 14 |
| 闪避冷却 | 4s |
| 闪避无敌 | 0.2s |
| 规则槽 | 1 个弹道 + 1 个命中；每条最高 3 级 |
| 突变 | 每局最多 1 项 |
| 组合数 | 3 弹道 × 3 命中 = 9；× 3 突变 = 27 类方向 |
| 敌人 | 6 普通 + 2 精英 + 1 三阶段 BOSS |
| 房间 | 8 普通 + 2 精英 + 2 事件 + 1 BOSS = 13 |
| 奖励 | 每房结束三选一；前两房保证弹道/命中各一条 |
| 事件 | 4 种，每局随机 2 种 |
| 存储 | localStorage；静态托管；首版无后端 |

### 2.2 9 种组合（文档已命名）

| 弹道 \ 命中 | 燃烧 | 冰霜 | 爆裂 |
|---|---|---|---|
| 贯穿 | 赤焰穿心 | 极寒贯穿 | 爆破穿甲 |
| 弹射 | 连锁焚烧 | 霜雷网络 | 雷暴连锁 |
| 散射 | 火焰弹幕 | 冰晶散华 | 裂爆风暴 |

这 9 个名字/描述可以直接作为游戏内组合图鉴与测试用例名称；机制由统一管线生成，不需要 9 个技能类。

### 2.3 15 分钟节奏核算

- 8 普通房 × 55s = 440s
- 2 精英房 × 80s = 160s
- 2 事件房 × 约 20s = 40s
- BOSS 约 180s
- 房间切换/奖励选择 13 次 × 约 8s ≈ 104s
- 合计约 924s ≈ **15.4 分钟**

结论：文档的 15 分钟目标在数学上成立。但 55s/80s 是**目标值**，需要波次导演和数值表保证；如果每房拖到 70s，整局会变成 18–20 分钟。建议把它当软目标，不做硬性倒计时。

### 2.4 硬边界（必须写进测试）

- 一次基础攻击最多触发 3 次命中规则。
- 爆炸/燃烧伤害不会再触发其他规则。
- 弹射不得重复选择已命中目标。
- 冰霜减速不能无限叠加，只能刷新/取最高值。
- 规则替换后旧效果立即失效，新效果即时生效。
- 房间切换销毁旧敌人/弹幕，玩家构筑保留。
- 死亡、暂停、失焦时所有逻辑停止，结算正确。
- 不允许无限递归/无限连锁。

### 2.5 首版明确不做

真正随机迷宫、多角色职业、复杂装备背包、多主动武器、联机账号、大型成长商店、数十种遗物/技能。首版用固定房间顺序 + 随机敌人配置 + 随机奖励验证重玩性。

## 3. 技术可行性

### 3.1 环境核验

本次实际检查：

- Node 22+、npm 11、git 可用；npm registry 可访问。
- Phaser 3.90.0 与 Phaser 4.2.1 均可获取；Vite 8.3.5 可获取。
- 本机有 Chrome / Edge，可做浏览器冒烟测试。
- 当前开发环境没有接入真实中端手机；移动端只能先做视口模拟，最终需真机验收。

### 3.2 推荐技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| 引擎 | **Phaser 3.90.0** | 成熟的 Arcade Physics、输入、场景、对象池、粒子；文档推荐；资料多 |
| 语言 | TypeScript | 规则/状态/结算有明确类型，利于 AI 生成后审查 |
| 构建 | Vite | 启动快、静态构建、易于单文件打包 |
| 测试 | Vitest | 纯逻辑单元测试，跑得快 |
| UI | Phaser 场景 + DOM/CSS 覆盖层 | 竞技场用 Phaser；HUD/弹窗/摇杆用 DOM，响应式和中文字体更稳 |
| 存储 | localStorage | 设置、最佳记录；不做中途存档 |
| 后端 | 无 | 静态托管即可 |

不推荐首版上 Phaser 4.2：它是新大版本，API/文档/社区案例的确定性不如 3.90；本项目不需要新渲染特性。也不推荐从零写 Canvas 引擎：场景、输入、对象池、物理、粒子都要自己补，反而增加审核面。

### 3.3 建议架构

```text
Phaser RunScene（竞技场、输入、渲染）
        │ 命令 / 事件
        ▼
RunController ── RoomDirector ── RewardSystem ── EventSystem
        │
        ▼
AttackResolver（纯 TypeScript，不依赖 Phaser）
  BaseAttack
    → TrajectoryResolver（选目标/弹道）
    → ImpactResolver（状态/范围）
    → DamageSystem（统一扣血/死亡）
        │
        ▼
CombatEvent[] → VFX / HUD / 音频
```

关键原则：

- **逻辑与渲染分离**：`AttackResolver`、状态、伤害、房间状态都是纯 TS，可在 Vitest 中跑，不需要浏览器。
- **数据驱动**：规则、敌人、房间波次、事件、突变、BOSS 阶段都放配置；新增内容主要改配置 + 小处理器。
- **统一结算**：所有伤害走一个入口；用 `TriggerBudget` 记录本次基础攻击的命中规则触发次数；DOT/爆炸伤害带 `canTrigger=false`。
- **游戏时间**：所有计时用游戏时钟/累加器，不用 `setTimeout`；暂停/失焦才能真正停住。
- **对象池**：魔弹、敌方弹幕、伤害数字、粒子、拾取物复用；限制峰值。
- **随机种子**：刷怪/奖励/事件用 seeded RNG；便于复现 bug 和自动化整局模拟。
- **调试钩子**：无敌、秒杀、跳房、指定规则、加速时间、显示碰撞体；只在 dev 构建开启。

### 3.4 为什么 9 种组合不会变成 9 套技能

统一执行：

```text
基础攻击
  → 弹道规则（贯穿/弹射/散射）
  → 命中目标集合
  → 命中规则（燃烧/冰霜/爆裂）
  → 伤害与状态结算（有限触发）
```

对应关系：

- 贯穿 + 爆裂：一枚弹最多穿 3 个目标，每个有效命中点最多触发一次爆炸；爆炸伤害不再触发爆炸。
- 弹射 + 燃烧：弹射在最多 3 个不同目标间跳；每个目标挂燃烧；燃烧 tick 不触发弹射。
- 散射 + 冰霜：3 枚扇形弹各自施加/刷新减速；减速取最高值，不无限叠加。
- 其余组合同理，只是目标集合和命中处理不同。

需要写测试的“讨厌情况”：

| 场景 | 期望 |
|---|---|
| 贯穿 + 爆裂打 3 个紧贴敌人 | 最多 3 次爆炸；爆炸不递归 |
| 弹射 + 燃烧打死目标 | DOT 不触发弹射/爆炸 |
| 散射 + 冰霜连续命中同一目标 | 减速刷新，不叠加到 100% |
| 规则替换 | 旧规则状态清理；新规则下一次攻击生效 |
| 房间切换 | 旧弹幕清空；玩家规则/HP 保留 |
| 暂停/失焦/死亡 | 计时、DOT、BOSS 技能全部停止 |

### 3.5 敌人、BOSS、房间的实现方式

- 6 种普通敌人复用 4 类行为：追击、保持距离射击、预警冲锋、死亡效果；每种敌人加参数/小状态机。
- 2 个精英是行为变体，不是新 AI 框架：雷暴精英多道雷击 + 锁定预警；裂甲精英连续两次冲锋，第二次追踪。
- BOSS 用一个阶段控制器：按 HP 阈值切换技能表；阶段切换时清弹/短暂无敌/明确 UI；第三阶段封印区 = 预警 → 判定 → 命中则禁用一条规则 4s（HUD 倒计时）→ 自动恢复。
- 房间用固定顺序 + 配置化波次；每房开始前预览敌人类型；普通房最后一批怪清完即结算，规则碎片自动吸附，避免追落单怪。

### 3.6 移动端与 UI

- PC：WASD + Space；自动瞄准最近目标；闪避方向建议跟移动方向，站定时跟朝向（需确认）。
- 手机：左侧虚拟摇杆 + 右侧闪避按钮；支持多点触控（移动 + 闪避同时按）；自动攻击不需要右摇杆。
- 响应式：`100dvh` + safe-area inset；HUD 不被刘海/手势区遮挡；横竖屏切换不丢状态。
- 失焦/切后台：立即暂停，音频暂停；恢复时给短暂准备时间，避免回来就被弹幕打。
- 中文文本：优先 DOM UI，避免 Phaser 字体渲染/缩放问题。

### 3.7 测试与部署

- Vitest：规则组合、触发预算、状态刷新、奖励/替换、事件修饰、BOSS 阶段、RunState 重置。
- 浏览器冒烟：启动、移动、闪避、开奖励、进 BOSS、死亡/重开；用 Chrome/Edge + 截图/控制台检查。
- 整局模拟：debug 模式下加速/跳房，跑通 13 房、胜利、失败、重开；再做一次完整手动 15 分钟。
- 性能：峰值弹幕/敌人数量压测；对象池复用；目标桌面 60fps，中端手机 30–60fps。
- 部署：`vite build` 输出静态站点；可选 `vite-plugin-singlefile` 打包成单 HTML，方便分享/手机打开。首版不需要后端。

### 3.8 技术未知/外部依赖

| 项 | 说明 | 影响 |
|---|---|---|
| 真机性能 | 当前只能浏览器模拟，缺少真实中端手机 | M5 验收必须补真机 |
| BGM | 没有音乐生成工具；可用 WebAudio 程序化氛围音或 CC0 音乐 | 不影响功能；影响完成度 |
| 美术一致性 | AI 生成像素素材的风格/透明边缘/动画帧需要清理 | 决定“像不像设计稿” |
| 音频授权 | 若用外部 BGM/音效，需要确认许可 | 发布前必须处理 |

## 5. 主要风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 3 分钟不好玩 / 15 分钟拖 | 中高 | 高 | 先做 M0+规则切片；数值全配置；试玩后再全量 |
| 构筑中期就封顶，后半段重复 | 中 | 中 | 规则等级改行为而非纯数值；房间敌人组合升级；事件修饰；必要时缩短到 10–12 分钟 |
| 规则递归/无限触发 | 中 | 高 | TriggerBudget、DOT/爆炸禁触发、弹射 visited set、专项单测 |
| BOSS 不公平（封印/减速） | 中 | 中高 | 清晰预警、i-frame 可躲、封印不永久、BOSS 控制抗性、限频 |
| 手机看不清/卡顿 | 中 | 高 | 高对比预警、弹幕上限、对象池、UI 安全区、真机验收 |
| 美术/音效不统一 | 高 | 中 | 早定调色板/像素规格；程序化占位先跑通；最后统一替换 |
| 15 分钟房间拖时长 | 中 | 中 | 波次导演 + 清场结算 + 碎片自动吸附；目标时长软约束 |
| 跨局状态污染 | 低–中 | 高 | 新 RunState、场景重启、清池/清计时器；连续重开测试 |
| AI 生成代码难审 | 中 | 中 | 每批 3–5 文件；先接口/边界后实现；纯逻辑测试；里程碑评审 |
| 范围膨胀 | 中 | 中 | 严格执行“首版不做”清单；meta/联机/背包一律后置 |

最需要提前验证的不是代码，而是：**玩家是否愿意为了规则组合去拉扯聚怪，以及 BOSS 第三阶段封印是否“看得懂、躲得掉、不憋屈”。**

## 6. 工作量与实施路线

### 6.1 代码量预估

- 约 8,000–12,000 行 TS/配置/样式（不含 Phaser 依赖）。
- 约 50–70 个源文件；30–50 个单测用例。
- 核心逻辑可测试部分约 3,000–4,000 行，是审核重点。

### 6.2 建议里程碑

| 阶段 | 交付 | 验收 | 预计有效日 |
|---|---|---|---:|
| P0 决策/脚手架 | 目录、Vite/TS/Phaser、调色板、调试钩子 | 空白场景可跑、可热更新 | 0.5 |

| P2 M1 规则 | 3+3 规则、9 组合、3 级、替换/升级、单测 | 9 组合生效；无递归；替换即时生效 | 1.5–2.5 |
| P3 M2 房间闭环 | 6 敌人、波次、碎片、三选一、3 房推进 | 从零打通 3 房；构筑变化可见 | 2–3 |

| P5 M5 移动/音频/性能 | 摇杆、响应式、音效、对象池、静态构建 | PC + 手机浏览器可完整玩；真机验收 | 2–3 |
| P6 M4 调优 | 数值、节奏、BOSS、反馈、试玩修正 | 5–10 人试玩；多种构筑可用；死亡原因清楚 | 3–5 |

> 实施顺序建议把移动端输入从 P1 就抽象好、P3 开始接触控，而不是等到最后；否则 UI/手感返工成本高。

### 6.3 首个切片（建议下一步）

目标：验证文档的“NEXT ACTION”，不做全量内容。

- 1 个房间、1 个玩家、2 种敌人（铁刺甲虫 + 雷光蝠）。
- 基础魔弹、自动瞄准、WASD/摇杆移动、Space/按钮闪避。
- 可夺取「弹射 + 爆裂」：弹射最多 3 个目标、每个落点爆炸、爆炸不递归。

- 死亡/重开；60fps 目标；无 console 报错。
- 验收：玩家会主动聚怪/拉扯，能感到“规则改变攻击方式”，愿意再开一局。

## 9. 待你确认的 3 个决策

### 决策 1：移动端形态（最重要）

- **A. 横屏优先**：手机提示横屏；弹幕可视性最好，最公平；不完全满足文档“支持竖屏”。
- **B. 竖屏优先**：纵向竞技场；手机握持自然，符合“支持竖屏”；PC 两侧留白/侧栏。
- **C. 方形响应式竞技场（推荐）**：同一逻辑场，横竖屏都能完整看到；PC 侧栏放构筑，手机上下放 HUD/操作；公平性和适配折中。

> 推荐 C；如果手机是主战场，选 B 更稳。这个决定会影响相机、UI、BOSS 弹幕和房间布局，越早定越好。

### 决策 2：美术目标

- **A. 低成本程序化/像素占位**：最快跑通，风格统一，视觉上限较低。
- **B. AI 生成像素素材 + 清理**：更接近设计稿，但需要统一规格/透明边缘/动画，时间更长。
- **C. 混合（推荐）**：菜单/过场用设计稿风格 AI 图；战斗内用统一调色板的程序化像素/矢量 + 光效；先保证可读性和手感。

### 决策 3：技术栈

- **A. Phaser 3.90 + TypeScript + Vite + Vitest（推荐）**：与文档一致，成熟稳定。
- **B. Phaser 4.2 + TS + Vite**：更新，但 API/资料确定性较低，本项目无必要。
- **C. 纯 Canvas 2D + TS + Vite**：更小、更可控，但要自己补场景/物理/输入/对象池，工作量更大。

另有一个默认范围（不单独列为决策）：**严格按文档首版**，不做 meta 成长、联机、背包、多角色；只存设置/最佳记录。

## 10. 技术卡点与素材落地方案（补充）

### 10.1 有没有硬卡点？

**没有“做不出来”的硬卡点。** 但有 4 个软卡点，需要靠工程手段 + 试玩验证，而不是靠某个库或某个素材一键解决。

| 软卡点 | 具体问题 | 是否阻塞 | 解法 | 仍需外部条件 |
|---|---|---|---|---|
| 移动端性能与可读性 | 弹幕、粒子、触控遮挡、竖屏视野 | 否 | 对象池、峰值上限、高对比预警、响应式 HUD、真机压测 | 需要一台真实中端手机验收 |
| 规则组合边界 | 递归、无限减速、重复弹射 | 否 | 统一结算管线、TriggerBudget、visited set、专项单测 | 无 |
| BOSS 公平性 | 封印区、减速、召唤物、阶段切换 | 否 | 明确预警、i-frame 可躲、封印倒计时、BOSS 控制抗性、限频 | 需要试玩校准 |
| 素材一致性 | AI 图风格、透明边缘、动画帧 | 否 | 统一调色板/轮廓/像素规格；程序化动画；保底几何素材 | 风格验证包 + 人工筛选 |
| 15 分钟乐趣与节奏 | 房间是否拖、构筑是否早封顶 | 否 | 3 分钟切片先行、数值全配置、波次导演、试玩 | 必须人工试玩 |
| 音频品质 | BGM 没有专业作曲 | 否 | SFX 全部程序化合成；BGM 程序化氛围音或 CC0 | 若要专业 BGM，需外部素材/授权 |
| 浏览器差异 | iOS 音频解锁、100dvh、Pointer 捕获 | 否 | 已知兼容写法 + 设备矩阵测试 | 真机/多浏览器 |
| 跨局状态泄漏 | 计时器、旧弹幕、旧状态 | 否 | RunState 重建、场景重启、清池、连续重开测试 | 无 |

**唯一不能在当前环境完全验证的是“真机移动端体验”**：性能和触控手感必须用真实手机跑一遍；代码层面可以先按移动端约束设计。

### 10.2 素材能不能全部搞定？

**能保证每个素材槽都有可用的、风格统一的版本；不能空口保证达到设计稿那张 AI 插图的精细度，也不能保证专业作曲级 BGM。** 这是两件事：

- **功能完整性**：可以做到 100%——每个规则、敌人、事件、BOSS、UI 状态都有视觉与音效，没有缺图、没有静音、没有占位符上线。
- **视觉上限**：取决于你选的美术目标；低成本程序化/像素风可以做到“统一、清楚、有氛围”，但不会像手绘 2D 大作；要接近设计稿质感，需要更多素材筛选与清理时间。

| 素材/表现 | 首选做法 | 把握 | 保底做法 |
|---|---|---|---|
| 主菜单/过场 | 设计稿风格 AI 图 + CSS 排版 | 高 | 渐变 + 程序化符文/粒子 |
| 玩家 | AI 概念图或程序化像素，2–4 帧 + 程序化动效 | 高 | 几何法师剪影 + 光效 |
| 6 种普通敌人 | AI 精灵图 + 调色板量化/描边/透明清理 | 中高 | 程序化剪影（甲虫/蝙蝠/花/史莱姆/浮灵/爆弹） |
| 2 种精英 | 基础敌人变体 + 额外光效/尺寸/颜色 | 高 | 放大 + 换色 + 额外技能特效 |
| 三阶段 BOSS | AI 底图 + 分层部件 + 程序化旋转/脉冲/变色 | 中高 | 几何构造体（核心/环/眼） |
| 地牢场景 | 程序化地砖生成 + 噪点/裂纹/符文装饰 | 高 | 纯色地砖 + 网格/暗角 |
| 弹道/爆炸/命中 VFX | Phaser Graphics + 粒子 + Additive 混合 | 高 | 纯代码几何特效 |
| UI/图标/构筑槽 | DOM/CSS + 内联 SVG | 高 | 纯文字 + 色块 |
| 中文字体 | 本机 Noto Sans SC / 微软雅黑；可打包 Noto 子集 | 高 | 系统字体 |
| 音效 | Python + ffmpeg 离线合成，或 WebAudio 实时合成 | 高 | 免费音效库（需授权确认） |
| BGM | Python 生成暗色氛围循环，或 CC0 音乐 | 中 | 环境 drone / 无 BGM |
| 角色动画 | 程序化 bob/tilt/squash/flash + 2–4 帧关键帧 | 高 | 无逐帧动画，只做位移/缩放/闪烁 |
| 掉落物/拾取 | 程序化图形 + 光柱/吸附动效 | 高 | 纯色菱形/圆点 |
| 结算/事件插画 | CSS/SVG + 图标 + 少量 AI 图 | 高 | 纯 UI 排版 |

结论：**素材不会成为“能不能做完”的阻塞项，只会影响“最终有多好看/多好听”。** 每个素材槽都有保底方案，任何阶段都不会因为缺图停摆。

### 10.3 本机已核实的素材工具链

- Python 3.14 + Pillow 12.2：裁切、去底、调色板量化、描边、拼图集、生成地砖。
- ffmpeg 9.0.2：音频格式转换、音效拼接、BGM 导出。
- 本机已有 Noto Sans SC（OFL）与微软雅黑，中文 UI 不需要额外找字体。
- npm 可获取 `sharp`、`vite-plugin-singlefile`、`@fontsource/noto-sans-sc`，可用于图像处理和单文件构建。
- Phaser 3.90 / Vite / Vitest 已核实可安装。
- 没有 ImageMagick，但 Pillow + sharp 足够；没有专业音乐生成工具，BGM 用程序化或 CC0。

### 10.4 素材生产流水线（打算怎么做）

1. **定风格令牌**：沿用设计稿的暗色地牢调色板（背景 `#080e19`、面板 `#121c2d`、青 `#65dcf0`、紫 `#b69bff`、橙 `#ffac68`、红 `#ff7186`、绿 `#7edca9`、黄 `#ffe399`），定玩家/敌人/BOSS 的逻辑尺寸、描边宽度、光源方向。
2. **先出源素材**：AI 生成角色/敌人概念图（纯色背景、无文字、统一俯视 3/4 视角、统一光源），或程序化几何/像素图。关键不是一次生成完美，而是先有可筛选的候选。
3. **脚本化后处理**：Pillow 做裁切、去底、调色板量化、1–2px 深色描边、统一尺寸；输出 PNG/WebP 和图集 JSON。AI 图的透明边缘和色偏在这一步统一。
4. **动画策略**：不做传统 8 方向逐帧行走。这个游戏是俯视自动攻击，玩家和敌人只需要“漂浮/倾斜/压缩/闪白/残影/蓄力”等程序化动效；特殊动作（冲锋、BOSS 阶段）再加 2–4 帧。这样既统一又省时间，也更适合手机小尺寸。
5. **在引擎里验证**：做一个“素材预览场景”，把玩家、2 个敌人、BOSS 剪影、HUD、地砖、弹幕放在同一屏；分别在 1440×900 和 390×844 截图，检查剪影、对比度、遮挡和手机可读性，再定稿。
6. **打包优化**：图集合并、WebP/PNG 压缩、音频 OGG/WebM、预加载；控制首屏体积，弹幕/粒子走对象池。
7. **授权记录**：每个外部素材记录来源/许可；AI 图记录生成方式；字体用 OFL；CC0 BGM 保留授权页。发布前统一检查。

### 10.5 视觉与可读性规则（比“画得好看”更重要）

- **低饱和背景 + 高饱和规则特效**：背景灰蓝/暗紫，玩家、敌人、弹幕用高明度色，形成对比。
- **形状语言区分敌人**：甲虫=装甲椭圆、蝙蝠=翼形三角、孢子花=放射形、史莱姆=软团、浮灵=拖尾幽灵、爆裂甲虫=圆壳+引线；即使小尺寸也能靠剪影辨认。
- **规则颜色固定**：燃烧=橙、冰霜=青、爆裂=黄白；贯穿=紫线、弹射=电蓝折线、散射=粉色扇面；同时用线型/图标辅助，不单靠颜色（色盲友好）。
- **预警必须“颜色 + 图案 + 轮廓”**：冲锋直线、爆炸圆圈、封印区域用斜纹/脉冲边框；不能只靠红色。
- **反馈优先级**：闪白 > 击退 > 伤害数字 > 屏幕轻震 > 粒子；粒子不能遮挡敌人和预警。
- **手机尺寸优先验收**：所有 UI 以 390px 宽为下限检查；触控目标不小于 44–56px；HUD 避开 safe-area。

### 10.6 音频方案

- **音效**：全部可程序化合成/离线生成，不依赖外部版权。包括：命中、爆炸、燃烧 tick、冰霜命中、闪避、受伤、拾取、规则升级、精英预警、BOSS 阶段切换、封印命中/解除、胜利/失败。
- **BGM**：两条暗色氛围循环（探索/ BOSS），用 Python 生成 drone + 脉冲 + 稀疏琶音，再用 ffmpeg 导出；如果听感不够，替换为 CC0 音乐或你提供的曲子。BGM 不影响功能完整性。
- **实现细节**：首次用户手势解锁音频；失焦/暂停时停音频；音量设置；BOSS 阶段可做轻微 ducking；不自动播放。

### 10.7 各阶段的素材策略（保证不阻塞开发）

| 阶段 | 素材状态 | 目的 |
|---|---|---|
| P0 风格验证 | 玩家 + 2 敌人 + BOSS 剪影 + HUD + 地砖 + 1 个 VFX | 先验证风格/可读性，不写全量逻辑 |
| P1 M0 切片 | 程序化占位 + 合成音效 | 验证 3 分钟手感，不被美术拖住 |
| P2 M1 规则 | 规则色/线型/图标 + 程序化 VFX | 让 9 组合一眼能区分 |
| P3 M2 房间 | 6 敌人精灵图 + 地砖 + 奖励 UI | 形成完整房间观感 |
| P4 M3 全流程 | BOSS 分层图 + 事件/突变图标 + 结算 | 完成全流程表现 |
| P5 M5 移动/音频 | 触控 UI、最终音效、图集/性能优化 | 双端可玩 |
| P6 M4 调优 | 统一描边/色彩/动效，替换所有占位 | 发布级一致性 |

### 10.8 建议先做“素材风格验证包”（0.5 天）

在写完整游戏前，先交付一个**纯视觉验证页**，成本很低，但能提前回答“素材能不能搞定”：

- 1 张主菜单构图（DOM/CSS + 设计稿风格图）。
- 1 张竞技场屏：玩家 + 2 种敌人 + BOSS 剪影 + HUD + 地砖 + 弹幕/爆炸。
- 同屏输出 PC 1440×900 与手机 390×844 两个尺寸。
- 检查：剪影是否一眼区分、预警是否清楚、颜色是否协调、手机是否看得清、是否有“廉价占位感”。
- 通过后再进入 M0 切片；不通过就只调风格，不返工玩法代码。

## 11. 最终判断

**能做，而且可以完整做出来。** 这个设计的聪明之处是把内容控制在“3 条弹道 × 3 条命中 × 3 个突变 + 6 敌人 + 2 精英 + 1 个三阶段 BOSS”，并用统一结算管线避免 9 套技能代码；这正是小团队/AI 辅助最擅长的规模。

技术上没有硬卡点，素材上也有完整的保底链路：**程序化占位 → AI 辅助精修 → 引擎内可读性验证 → 最终统一打磨**。真正的风险仍然在三件事：

1. 3 分钟切片是否足够好玩；
2. 15 分钟内构筑是否持续有变化、房间是否拖；
3. 手机端是否看得清、按得准、跑得动。

建议按文档的决策门槛执行：先做“素材风格验证包”（0.5 天），再做 3 分钟切片，确认“夺取弹射 + 爆裂后，玩家会主动聚怪”这个时刻成立，再扩展完整 15 分钟。若切片不好玩，先修战斗反馈、规则取舍和敌人行为，不要靠加内容补救。
